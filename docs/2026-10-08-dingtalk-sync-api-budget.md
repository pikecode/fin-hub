# 钉钉同步 API 调用次数优化

## 原因

- 原客户端每次业务请求都调用 OAuth 获取 access token，分页、部门树、审批详情和节点查询均重复获取。
- 自动同步每小时对全部40个模板查询节点，未变化和未启用模板也查询，最近一轮40次均失败。
- 已完成且解析成功的近30天审批，在两天重叠窗口内每小时反复拉详情。解析异常单据的24小时冷却此前只在历史补偿阶段生效。

## 实现

### 凭证缓存

同一进程内按 API 地址、应用标识和密钥摘要隔离缓存，跨客户端实例复用。按响应 expireIn/expires_in 的有效期缓存并提前刷新；缺少或非法有效期不缓存。加锁避免并发重复请求，限制缓存条目数量。新旧接口遇到凭证失效时进行有界刷新重试，保留QPS限流退避。手动连接测试强制发起真实凭证请求。

凭证不写入同步统计、业务数据库或文件。内存缓存按服务进程隔离，进程重启后重新获取。

### 审批详情

开启 skip_existing 时：

- 未完成审批仍每轮检查，以发现审批完成和后续状态变化。
- 近30天已完成审批和已完成但解析失败的审批，最近一次解析未满24小时不重复拉取。
- 超过30天、成功解析且关联门店的稳定单据继续沿用既有跳过策略。
- 撤销、拒绝审批不重复拉取。
- 历史未完成审批与解析异常补偿继续保留，分页、游标恢复和水位推进规则不变。

手动同步选择 skip_existing=False 时，查询窗口内审批可强制刷新，不受冷却限制。已完成审批后续源数据变动通常在下一次每日复查时发现，不承诺每小时刷新已完成单据。

同步摘要新增 detail_fetched_count、detail_skipped_count，统计逻辑层详情查询次数与跳过数量，QPS底层重试另计。

### 模板节点

模板清单和名称仍每轮同步；自动节点查询改为每24小时最多一次，仅对启用模板查询。节点失败也按每日重试，避免权限或参数问题每小时反复消耗调用。手动模板同步仍立即刷新节点。统计新增 node_attempted、node_skipped；审批同步失败时也保存模板阶段统计，避免丢失节点冷却依据。

### 部门树去重

原遍历为每个子部门查询下级，用于识别门店，递归到这个子部门时又重复查询同样的下级。增加仅限本次遍历的结果缓存，包括空的叶子部门结果；两处逻辑共享同一查询结果，每个部门最多查询一次。下一轮清空缓存重新拉取，门店名称变化及新增子部门仍会发现。保留深度限制、门店结构识别和每个真实请求后的限流间隔。

部门树和门店名称仍按原频率同步，不通过降低门店同步频率节省调用。

## 本地验证

六个钉钉测试文件共104项通过：凭证跨实例及并发复用、有效期及缺失有效期、失效重试、强制连接测试、每日审批刷新、未完成审批刷新、强制全量刷新、节点每日刷新及启用范围、分页和漏单补偿。

模拟100次业务请求：业务接口100次，OAuth接口1次；旧实现对应100次OAuth。因此该场景总调用由200次降为101次，减少49.5%。这是受控测试结果，不作为所有生产同步的固定降幅。

## 服务器实测（第一阶段完整同步）

验证任务 6941d0c407404cb1b13b6cf7b1702631 拉取完成，耗时84.6秒：OAuth请求1次、模板列表1次、审批分页13次、审批详情65次。跳过40次节点查询、61次详情查询。该轮部门请求仍为203次，随后据此补充部门树去重优化。

本轮15条审批费用解析异常保留在原记录中，拉取完成且水位正常推进；2条来源不存在审批仍按原补偿规则处理。调用优化不更改这些单据的费用金额、手工分类和业务归属。

验证输出存于发布目录 verification.jsonl；部门树第二阶段实测存于 department-verification.jsonl。首页、登录页、API健康检查和未登录权限检查通过。

## 部门树最终实测

第二阶段只读验证：部门API由203次降至102次，OAuth1次，耗时33.85秒。仍返回101个部门、34个门店候选，部门ID及名称与当前启用快照完全一致，没有遗漏。部门数据未因验证写入数据库。

最终服务器镜像核验为 deploy-20261008-sync-api-budget-v2，重启次数0；发布后健康检查通过。
