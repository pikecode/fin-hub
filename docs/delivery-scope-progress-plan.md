# fin-hub 交付范围、进度评估与开发节奏

更新时间：2026-09-01 11:19 CST

## 1. 文档目的

本文件用于收敛后续开发，避免继续做分散、低优先级或难以验收的功能。

后续开发以“可交付闭环”为标准，不以“页面数量”或“接口数量”为标准。每轮开发都应能回答：

- 是否推进了门店财务处理主流程？
- 是否降低了上线、验收、运营或数据风险？
- 是否有清晰验证证据？
- 是否会引入需要回头返工的交互或数据模型？

## 2. 当前技术方案

### 2.1 三个项目

| 项目 | 路径 | 技术 | 定位 |
| --- | --- | --- | --- |

## 3. 目标交付范围

### 3.1 必须闭环

1. 后台门店套帐主流程
   - 当前维护人员进入自己负责的门店。
   - 选择门店和账期。
   - 管理银行流水。
   - 管理审批单。
   - 维护营业收入。
   - 完成支出和收入对账。
   - 通过封账预检后封账。

2. 后台报表闭环
   - 按门店和账期查看财务汇总。
   - 查看营业收入、收入渠道、分类支出、供应商支出、未匹配流水。
   - 导出 CSV / Excel。
   - 报表口径与封账数据一致。

3. 股东小程序闭环
   - 股东用授权码登录。
   - 只能查看授权门店。
   - 只能查看已封账账期。
   - 支持门店列表、账期选择、汇总、趋势、渠道分析。

4. 权限和数据安全闭环
   - 管理员、财务人员、只读人员、股东访问范围清晰。
   - 密钥不明文泄露。
   - 生产环境启动前能检查必要配置。
   - 关键操作有审计日志。

5. 部署和运维闭环
   - 数据库迁移可执行。
   - 本地启动路径清楚。
   - 生产配置样例清楚。
   - 数据库备份、诊断导出、任务状态可查看。

### 3.2 暂不作为首版交付范围

这些功能可以规划，但不应阻塞首版交付：

- 智能匹配复杂算法和机器学习。
- 字段映射的高级可视化配置器。
- 报表自定义大屏。
- 多租户 SaaS 化。
- 独立任务调度平台。
- 对象存储、CDN、分布式缓存。
- 小程序复杂权限自助申请流程。

## 4. 当前进度评估

### 4.1 总体判断

当前项目已经不是空骨架，核心模型、主要接口和主要页面都已存在，但还没有达到“完整可交付”。

主要原因：

- 主流程已经大体可走，但还需要按“真实用户路径”逐页验收。
- 有些功能已经编码，但验证粒度还偏技术测试，缺少端到端验收脚本或验收清单。
- 当前工作树有大量未提交改动，需要先稳定，不适合继续大范围发散开发。
- 部分最近新增能力，例如当前用户门店接口，处于“已编码、待全量验证和文档闭环”状态。

## 5. 开发原则

后续不再按“看到一个后续建议就开发一个功能”的方式推进。

开发顺序固定为：

1. 主流程闭环优先。
2. 验收缺口优先。
3. 数据安全和权限优先。
4. 运维上线优先。
5. 体验优化最后做。

每个功能进入开发前必须明确：

- 入口在哪个页面。
- 对应哪个 API。
- 涉及哪些表和权限。
- 成功和失败怎么反馈。
- 用什么测试或手工步骤验收。

验收：

- 股东能在小程序看到封账报表。
- 常见错误能通过页面提示或任务中心定位。

## 7. 建议节奏

### 每轮开发节奏

每轮只做一个明确主题：

1. 开始前确认目标属于 M0-M4 哪个里程碑。
2. 先读相关代码和文档。
3. 写最小必要改动。
4. 补测试或验收步骤。
5. 跑对应验证命令。
6. 更新本文件或对应模块文档。
7. 用简短结论说明“完成了什么、还剩什么”。

### 近期建议顺序

1. M0：收尾 `GET /api/auth/me/stores`，验证门店套帐入口按当前用户门店范围展示。
2. M0：整理 `.next` 备份目录策略和工作树状态。
3. M1：做一份“门店套帐端到端验收清单”，并按清单跑一次。
4. M1：处理旧版/新版页面并存的问题，减少菜单和用户路径混乱。
5. M2：核对后台报表和小程序报表口径。
6. M3：验证空库迁移、生产配置、备份和诊断脚本。

## 8. 风险清单

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 继续发散开发 | 功能多但不可交付 | 严格按 M0-M4 推进 |
| 真实钉钉环境未联调 | 审批数据同步可能上线后暴露问题 | M1/M4 使用真实或接近真实样本验证 |
| 新旧页面并存 | 用户不知道该用哪个入口 | M1 决定首版入口，隐藏或标记旧入口 |
| 报表口径漂移 | 后台和小程序金额不一致 | M2 用同一账期测试数据核对 |
| 权限测试不足 | 可能越权查看门店或报表 | M3 补跨模块权限回归 |
| 构建产物污染工作树 | 开发验证容易互相干扰 | M0 处理 `.next` 产物策略 |

## 9. 当前结论

当前适合继续开发，但不能继续散点开发。

正确节奏是：

1. 先完成 M0 稳定工作树。
2. 再围绕门店套帐主流程做 M1 验收。
3. 然后处理报表和股东小程序。
4. 最后做上线运维和体验打磨。

下一次开发应从 M0 开始，不再新增与 M0/M1 无关的功能。
