# 分红管理：门店期初数据与隔离月份

## 需求与范围

每家门店独立设置使用系统计算分红的第一个月份（数据隔离月份，包含该月），一次性录入此前历史期初数据，避免逐月补录，以及重复累计系统里已存在的早期数据。统一独立分红页、门店内分红页、全公司合并和财务报表读取口径。页面收窄、卡片和间距缩小，提高数据密度。

## 录入内容

入口“录入历史数据/维护期初数据”，弹窗包含：

- 数据隔离月份，中文年/月选择；旁边说明按钮解释：该月是第一个纳入系统计算的月份，之前（不含该月）的系统财务数据不参与分红累计，但不删除原始数据。
- 期初剩余未分配利润：隔离月份之前剩余的利润，可为负数。
- 历史累计利润：隔离月份之前累计净利润，可为负数。
- 历史累计分红：隔离月份之前已分红累计，非负。
- 筹建投入资金：非负，属于门店资料，不是当月增资。
- 筹建费用总支出：可空；未填读取筹建费用报表原金额去重累计支出，明确填 0 优先取 0。
- 累计运营增资：隔离月份之前运营注资累计，非负。
- 修改原因：必填，首次录入同样留痕。

保存前显示期初月份和金额摘要进行二次确认。金额最多两位小数。历史累计利润、累计分红与期初余额独立录入，不强制用两者差额覆盖期初余额。

## 计算口径

隔离月及以后：

- 本月净利润：财务报表净利润，不再由旧的固定 2026-10 日期决定。
- 本月可分配利润＝上月期末剩余未分配利润＋本月净利润。
- 期末剩余未分配利润＝本月可分配利润－本月分配利润。
- 隔离月的上月余额＝期初剩余未分配利润。
- 历史累计利润＝期初历史累计利润＋隔离月起截至查看月净利润。
- 历史累计分红＝期初历史累计分红＋隔离月起截至查看月分红。
- 累计运营增资＝期初累计运营增资＋隔离月起截至查看月注资。注资不增加利润余额。
- 财务报表“累计增资”＝筹建投入＋累计运营增资。

图片中后续月份余额公式缺少“本月净利润”，采用上述完整递推，分别展示分配前可用利润与分配后期末余额，避免混淆。不因缺少某个月的业务记录跳过其利润，按连续月份计算。

## 隔离与历史兼容

- 仅在财务人员明确保存期初设置后启用新口径；未配置门店继续沿用旧规则，页面提示待确认期初，不能自动猜测或迁移已有手工余额。
- 隔离月以前历史记录保留、可查看明细及留痕，标注“隔离前，不参与计算”，不可新增或修改分红、增资及手工利润，不计入新累计。
- 隔离月起禁止逐月手工覆盖净利润/期末余额，改用期初入口维护历史起点。
- 全公司合并仍只读，按每店自己的起点计算后汇总；查看月份早于某店起点时，该店隔离前数值不加入合并金额。未配置或缺少余额的门店不能被默认为已完整配置。
- 配置后 GET 仅读取汇总，不创建空白分红月份或账套。更新分红或锁定月份才持久化月份记录。
- 筹建资料与上一轮新增字段共用同一份存储，期初配置后统一从期初入口维护，不允许旧筹建入口绕过版本、锁定和留痕。

## 修改保护与审计

仅管理员操作，校验门店权限和启用状态。配置、月度修改及锁定采用同一门店事务锁，保存包含版本检查，阻止覆盖他人的新修改。

新建期初：检查隔离月及以后；更改起点/金额：检查新旧起点较早月份及以后。如有受影响已锁定分红月份或已封账账期，拒绝修改，提示先解锁/解封。更改筹建金额时额外遵守筹建封账限制。配置不删除业务记录、不自动解锁。

每次保存记录旧值、新值、操作人、时间和原因；前端提供修改记录入口。保存失败弹窗内显示明确错误，提供 loading 和重复提交保护。

## 实施步骤

1. 新增门店期初表与 0035 迁移，复用筹建资料表；定义输入/响应结构。
2. 实现只读统一计算服务，接入分红 workspace 与财务报表补充接口，保留旧口径兼容。
3. 新增期初 GET/PUT，保护金额、版本、权限、锁定/封账；月度接口按配置动态判断。
4. 新增历史数据录入/确认/留痕弹窗；缩小页面和卡片；合并视图、历史表和金额名称同步。
5. 隔离测试：不同起点、跨月缺口、负利润、分红扣减、注资独立、隔离前排除、未配置兼容、并发版本、锁定保护、合并及报表一致；类型检查、生产构建及隔离数据视觉检查。

当前进度：开发及验证已完成，尚未部署。当前本地 API 连接生产库，本轮未执行生产迁移；业务验证使用隔离 PostgreSQL。

## 实现与验证结果（2026-10-27）

- `dividend_opening_balances` 保存每个门店独立起点、历史金额、版本与最后修改信息，迁移为 `20261026_0035`，依赖上一轮报表迁移 0034。
- `GET/PUT /api/dividends/opening/{store_id}` 查询/保存，`GET .../history` 返回该门店的修改记录和前后值；管理员、门店权限、金额、版本、锁定、账期及筹建封账均校验。
- 分红 workspace 和财务报表补充数据接入 `configured_history`。配置后的历史查询只读，连续补齐计算月份，既有单据保留；隔离前历史可见但不累计。隔离前已有锁定可通过解锁解除，以便将起点向前调整，不修改其交易金额。
- 未配置门店继续兼容旧日期口径，同时明确提示待确认期初；不存在自动识别期初余额的隐式迁移。
- 合并视图只纳入启用门店，各店按独立起点计算；排除隔离前当月利润、分红、注资及明细，保留未配置门店余额未知状态，显示配置提醒。
- 前端统一使用“录入历史数据/维护期初数据”，包含中文月份说明、六项金额、原因、保存前确认、修改记录、加载及错误反馈。旧独立筹建资料编辑入口已由此替代，旧 API 在期初配置后拒绝绕过维护。
- 页面最大宽度 1040px，三列紧凑卡片，补充分配前可用利润，明确期末余额；历史表每页 12 行，操作列固定，隔离前只读。
- 43 项隔离 API/回归测试通过，类型检查和 linux/amd64 生产构建通过；单独验证了不同起点的合并、隔离前明细排除及未知余额不按 0 处理。
- Chrome 中使用验证镜像与隔离响应数据检查了页面、金额回显、录入、保存前确认、隔离说明及修改记录弹窗。没有通过浏览器测试修改生产业务数据。
- 已离线生成 0033→0035 SQL；未部署、未提交 Git，也未执行生产库迁移。

## 发布与数据衔接

上线时先按增量部署文档备份，再执行 0034、0035 迁移，发布对应前后端。迁移只增加配置表，不替用户填写期初。每店由财务明确确认后启用。

已有门店保存期初前，应核对输入是否已包含旧手工余额当月的利润和分红，避免重复计入。保存后会影响起点及以后累计金额，锁定/封账冲突必须先处理，不能自动跳过。

一旦门店启用新期初，不能直接切回只理解固定 2026-10 规则的旧代码，否则会恢复错误口径；回退需连同期初配置、业务数据及计算版本制定恢复方案。
