# 小程序完整复刻 PC 财务报表：设计与开发方案

日期：2026-11-13。状态：已按方案实施并发布配套API/PC，小程序开发版本已上传；体验版设置和真机验收未完成，详见[实施记录](2026-11-13-miniapp-report-parity-implementation.md)。

基线：[PC 报表功能与统计口径汇总](2026-11-13-pc-financial-report-overview.md)，生产 PC 版本 deploy-20261113-paid。目标是小程序与 PC 的报表数据、字段、分组顺序、来源追溯和财务逻辑一致，布局适配手机。

## 1. 范围与导航

保留现有底部 tabbar 及顺序：报表、银行流水、分红管理、我的。报表内保留“财务报表 / 营业收入”，门店在左上角切换；月份选择、授权门店记忆及未封账查看继续保留。

本轮按现有股东只读定位设计：完整查看 PC 报表数据、凭证和导出；不新增目标、余额、匹配、计提、分红等业务写权限。PC 的目标和余额维护结果在小程序同步展示。未来如需移动财务操作，应另行定义角色、写入接口及审计。

不把 PC 的宽表压缩到手机。指标改为双列卡片，长表改为列表卡片和详情页，但保留全部业务字段；分类层级可展开，金额右对齐，百分比按 PC 精度展示。

独立“银行流水”和“分红管理”tab继续保留；从报表点来源进入已有流水详情或新增借款详情，不跳转到未授权的管理端网页。

## 3. 手机页面设计

财务报表按以下顺序排列，与PC一致：

1. 门店与月份、账期状态、数据更新时间及导出入口。
2. 门店营收及渠道收入。
3. 门店支出。
4. 资金流情况。
5. 利润分红。
6. 投入与累计。
7. 核心成本率结构。
8. 支出分类排行。
9. 各类别支出统计。
10. 计提与冲销费用。
11. 特殊流水。
12. 主要支出凭证。

提供页内章节导航，跳转到对应区域。核心指标首屏展示，列表按页/展开加载；空板块保留标题与“暂无记录”，不能让用户误以为功能缺失。

金额缺失不显示为0，区分待录入、隔离前、无数据及真实0。百分比分母为0显示“—”。筹建超支显示绝对值及明确标签。未封账提示数据会更新；封账状态不限制已授权用户查看。

“营业收入”子页保留渠道月度汇总和每日明细，按PC同一收入日期口径查询，分页及渠道字段一致。

## 4. 计算和数据复用

### 4.1 服务端唯一口径

沿用 PC 已有计算服务，小程序只负责展示，不重新计算入账金额或利润归属：

- 收入按收入日期；审批费用按审批入账月份。
- 单账期审批只计一次整单，多笔付款日期不影响归属；显式多账期方案按方案分摊。
- 实付模式使用后台累计有效实付及精确到分的明细分摊结果，不在手机端按匹配金额再分配。
- 计提整单关联排除全部审批费用；明细关联排除选中部分；计提/补提/冲销按自身月份体现。
- 非经营分类、分红、注资及外借本金遵循现有规则。
- 未封账、封账、分红期初隔离、筹建金额来源和人工报表余额含义一致。

### 4.2 接口方案

保留 `/api/miniapp` 专用认证入口。扩展现有 `/report` 或增加配套只读接口，调用已有月报、supplement、appendix及凭证服务。避免在miniapp router复制SQL实现。

| 数据 | 建议接口职责 |
| --- | --- |
| 核心月报 | 返回PC同源metrics、supplement、账期状态，增加契约版本/读取时间 |
| 分类统计 | 返回PC相同的分类树、分区、历史累计及占比数据；共享纯展示转换函数或后端组装，禁止两端各自猜层级 |
| 分类详情 | 按分类标识和月份分页，覆盖审批、计提、采购、直接入账等同源费用；区分费用日期与本期入账金额 |
| 计提/借款/主要凭证 | 提供元数据列表和鉴权下载，支持对应resource_type；目前仅expense_item的附件入口不够 |
| 特殊流水/业务附录 | 复用PC appendix的选择范围与来源关联，可分页，费用共享金额避免重复累计 |
| 导出任务 | 独立创建/查询/鉴权下载；详见下节 |

现有小程序 `/expenses` 主要围绕审批确认费用，不能直接当作PC所有分类明细的完整实现。实施时以PC明细服务为准，补齐采购、渠道费用、直接入账和计提等来源，并与分类汇总逐项对账。

保留已上线接口兼容性；新增字段优先可选，不能让旧体验版突然无法读取。所有数据接口、附件下载和导出文件均实时校验门店范围；授权撤销后不再允许读取旧文件或请求。

### 4.3 展示契约与代码结构

建议抽取：

- shared-types：报表展示DTO、费用来源、状态及详情/附件契约。
- 共享纯函数：指标分组、标签、百分比/金额格式、分类分区及排序；无React/Taro/DOM依赖。
- 小程序 FinancialReportPage：专管门店月份、加载状态和章节导航。
- SummarySections、RevenueChannels、CostStructure、CategoryTree、AccrualList、LoanList、SpecialTransactions、MajorVouchers等组件。
- 详情页：分类费用、借款事件、凭证列表、导出状态；流水继续用已有bank-detail。

避免继续往当前包含报表、流水、分红三种模式的store-workspace文件里堆全部报表代码。拆分时保持tabbar路径与门店选择行为兼容。

## 5. HTML/PDF 导出设计

PC目前主要在前端生成HTML/PDF。小程序没有同样的DOM/浏览器运行环境，因此需要新增导出基础设施，不能把“调用已有下载接口”当成已存在能力。

推荐让两端逐步复用同一份报告展示模型和导出模板，由服务端导出任务生成文件：

1. 用户选定门店月份及格式，发起导出任务。
2. 后台按同一读取事务获取报表、明细、附录与凭证，形成导出快照。
3. 任务生成HTML/PDF，返回状态及完成后的下载标识；不在单次API请求中长时间等待。
4. 小程序鉴权下载；PDF使用微信文件打开能力，HTML提供文件保存/转发及使用说明，不承诺在小程序原生页面直接打开HTML。
5. 权限变化重新校验；文件限定有效期并清理。失败区分数据获取、凭证下载和文件生成错误，允许重试。

导出内容与PC保持一致，包括“明细续行”、本期费用金额与银行金额区分、特殊流水、无流水费用及凭证。凭证缺失要提示，不将失败文件伪装成完整导出。

第一阶段PC可保留现有导出入口，服务端模板与现有模板逐项验证后再切换；不能在本轮重构中无验证替换PC导出逻辑。服务端PDF渲染依赖、队列/任务存储、文件存储/下载域名均需在开发阶段确认并验证部署资源。

## 6. 加载、授权与安全

- 门店切换立即清空旧数据，取消/忽略旧请求，不能显示上一家门店金额。
- 月份切换时summary、分类、详情必须属于同一门店月份；附录懒加载，避免巨型响应。
- 后台变动后支持下拉刷新；标记读取时间，避免“仍显示旧金额”无法判断。
- 请求失败显示重试，权限失效清空页面并返回重新登录/门店选择。
- 继续动态合并直接授权与门店分组授权；列表、详情、图片和导出一律校验。
- 小程序凭证不能调用管理端业务写接口；隐藏按钮不能替代后端权限校验。

## 7. 开发顺序与交付

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A：契约与口径 | 建立PC字段对照表、统一DTO/格式/分类转换，补齐同源读取接口和测试 | 同门店月份两端金额逐项一致，不改变现有生产报表 |
| B：完整报表页 | 拆分小程序组件，按PC顺序还原所有指标与图表/分类 | 12个页面区域完整，窄屏可读，tabbar不变 |
| C：明细与凭证 | 分类详情、借款事件、计提凭证、主要凭证、特殊流水及来源追溯 | 所有明细可访问且授权正确，汇总与明细一致 |
| D：导出 | 异步任务、文件生成/存储/鉴权下载、小程序文件操作 | 与PC报告对账一致，分页/续行/图片可用 |
| E：验收发布 | 端到端、真机、生产只读对账、分批发布与记录 | 后端先兼容上线，再上传新小程序体验版，验收后正式发布 |

B/C建议作为同一个“完整在线报表”交付批次；D为独立基础设施和导出交付批次。在D完成前只能声明在线报表对齐，不能声明已经完全复刻全部PC能力。

每批先建立before备份及work分支，更新CHANGELOG，验证后提交并建after备份。后端部署和微信上传独立记录；上传开发版本不等同于设置体验版或正式发布。

## 8. 验收清单

- 同门店月份逐项核对PC与小程序的字段、金额、比例、层级、排序和状态。
- 覆盖已封账、未封账、无收入、真实0、缺目标/余额、筹建缺来源及期初隔离月份。
- 同一审批单多笔跨月付款只计一个月份；显式多月方案、实付模式新增匹配/解除后金额正确。
- 整单/明细计提关联不重复入账，补提与冲销正负及分类金额正确。
- 分类明细金额和对应分类汇总一致，历史累计按截止月份；不能把分页当前页合计当总额。
- 手续费、采购、银行直接入账、非经营分类、分红/增资、借出及部分还款逐项验证。
- 授权门店/分组动态变动、跨店附件/详情/导出拒绝、账号失效及只读校验。
- 慢网、快速切换门店月份、重复点击、列表分页、长文字、图片失败及文件过期可恢复。
- HTML/PDF与同一数据快照对账，续页不重复金额、凭证不缺失、长报表布局可读。
- 微信开发者工具编译及至少iOS/Android真机检查；类型检查或浏览器桩测试不能替代真机验收。

## 9. 当前结论

本方案已完成在线报表和导出两批开发，配套API/PC已发布 `deploy-20261113-parity`，微信开发版本 `2026.11.13` 已上传。按现有需求默认保持股东只读；若要求小程序同时承担PC财务维护操作，则需追加权限和业务操作设计。完整复刻包含在线报表与导出两部分，必须按上述阶段分别验证并明确完成状态。
