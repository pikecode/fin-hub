# 钉钉审批同步改造方案

日期: 2026-09-04

## 目标

解决审批单历史缺失、状态更新漏同步、任务中断后无法可靠恢复的问题。

## 现状问题

1. 当前同步主要依赖审批提交时间窗口。
2. 历史任务中断后，部分窗口没有完整回补。
3. 审批修改时间虽然已入库字段，但没有形成独立的增量策略。
4. 自动同步水位线依赖迁移字段，当前本地库不完整，链路不稳定。

## 方案

### 1. 首次回补

- 仍按 `submit_at/create_time` 做历史窗口拉取。
- 按月或按较小窗口分段回补。
- 每段完成后再推进水位线。

### 2. 日常增量

- 以 `approval_watermark_at` 作为主水位。
- 每次同步保留 `approval_overlap_days` 重叠窗口。
- 通过 `approval_no` / `process_instance_id` 做幂等更新。

### 3. 修改补扫

- 利用 `dingtalk_modified_at` 识别状态、金额、明细变化。
- 对已存在且最近有修改的审批做重刷。
- 已匹配记录在审批内容变化后要回到待复核。

### 4. 断点恢复

- 分模板保存 cursor。
- 任务中断只保留未完成 cursor，不推进最终水位。
- 恢复时优先续跑，再补窗口。

### 5. 手动重刷入口

- 提供按 `dingtalk_modified_at` 时间窗口的重刷接口。
- 可按门店、模板、时间范围筛选。
- 适合补最近修改的审批单，以及人工修复后的重新入库。

## 实际落地逻辑

### 同步顺序

当前自动同步固定按下面顺序执行：

1. 拉部门快照
2. 同步部门到门店映射
3. 拉审批模板
4. 同步审批单

这样做的原因是审批单落库前必须先有门店映射和模板配置，否则只能生成未解析记录。

### 审批同步过程

每个审批模板单独拉取，按时间窗口分页获取 `process_instance_id`，再逐条拉详情并落库。

已落地的关键规则：

- 以 `approval_no` / `process_instance_id` 做幂等更新
- 已存在且稳定的审批单会跳过
- 最近修改过、状态不完整、解析/处理异常的审批单会进入重刷
- 处理过程中使用行锁，避免并发同步互相覆盖
- 模板分页会记录 `cursor`，中断后可继续续跑

### 数据处理

审批详情入库后，会继续处理：

- 审批主表 `approval_instances`
- 费用明细 `expense_items`
- 附件 `attachments`
- 门店归属、审批状态、解析状态、处理状态

如果审批内容后来发生变化，系统会再次拉取详情并重新解析，避免旧明细长期停留。

## 本次验证结果

这次在服务器上做了历史补回和门店核对，结果是：

- 自动同步任务已恢复为 `succeeded`
- `approval_watermark_at` 已推进
- `approval_resume_state` 已清空
- 你核对的门店审批编号都已入库且归属正确

中途发现过一个真实阻断：

- `attachments.external_file_id` 过短，钉钉附件有时会写入长 JSON
- 这会在历史回补时触发数据库截断
- 已改成 `Text`，并补了迁移

还有一个操作层面的事实：

- 大窗口历史回补可能只跑完一部分模板分页
- 这时会返回 `next_cursor`
- 需要按 cursor 继续跑，不能直接把窗口当成已完成

## 实施顺序

1. 修复自动同步所需迁移，补齐 `approval_overlap_days`。
2. 让自动同步稳定推进水位线。
3. 增加修改时间补扫。
4. 再做历史缺失回补任务。

## 验收标准

- 历史缺失审批可补回。
- 审批状态变更能被重新同步。
- 同步中断后可从 cursor 续跑。
- 自动同步不会再因为窗口切换漏单。
- 服务器上的自动同步任务稳定成功，水位线可持续推进。
- 附件字段长度不再阻塞审批回补。
