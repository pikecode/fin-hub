# 钉钉同步逻辑分析与问题确认

日期：2026-09-26

## 当前同步链路

自动任务由 API 进程启动的 asyncio 循环每 60 秒检查一次。到达 `next_run_at` 后，按以下顺序执行：

1. 拉取钉钉部门树。
2. 将部门快照同步为本地门店候选和门店映射。
3. 拉取审批模板及模板节点。
4. 只处理已启用模板的审批实例。

审批同步对每个模板分页调用钉钉接口，先取实例 ID，再逐条获取实例详情。详情会保存到：

- `approval_instances`：审批主记录和原始 JSON。
- `expense_items`：按字段映射解析出的财务明细。
- `attachments`：钉钉附件占位记录。

后续银行流水对账使用 `expense_items` 和审批主记录，不直接从钉钉原始 JSON 计算匹配金额。

## 增量、幂等与续跑

- 审批实例以钉钉实例 ID 幂等更新。
- 自动同步使用 `approval_watermark_at` 作为水位，并按 `approval_overlap_days` 回退窗口，避免时间边界漏单。
- 达到分页上限或任务失败时，把窗口和各模板 cursor 写入 `approval_resume_state`。
- 稳定完成、已解析且已关联门店，并且超过 30 天未变化的审批会跳过详情拉取。
- 未完成、无门店、未解析或处理状态异常的审批会进入重刷。
- 同步任务统一写入 `sync_jobs`，记录状态、窗口、计数、cursor 和摘要；运行中的钉钉同步任务会阻止并发启动。

## 已确认的问题

### 1. 任务成功计数与实际落地不一致（已修复）

`sync_real_instance()` 在以下情况仍保存审批原始数据并返回 `True`：

- 缺少门店或业务日期。
- 审批状态不可解析。
- 无法解析审批金额。

这些场景不会生成可用于财务对账的 `expense_items`，但上层会把它们计入 `success_count`。因此任务可能显示成功，实际只落了审批原始记录。

已修复：原始审批仍会保存，但上述情况返回解析失败，任务计入 `failed_count`，不会再计入 `success_count`。后续仍可增加独立的 `skipped_count`，用于区分业务跳过和真正接口失败。

### 2. 自动任务配置没有完全接入执行（已修复）

`DingTalkAutoSyncSetting` 中已保存以下配置：

- `root_dept_id`
- `max_depth`
- `page_size`
- `max_pages`
- `interval_minutes`

但自动执行仍使用路由模块的固定常量：部门根节点、部门最大深度、审批分页大小和最大页数没有读取设置值。调度时间使用 `scheduled_time` 计算 `next_run_at`，`interval_minutes` 当前没有参与调度。

已修复：自动任务现在读取部门根节点、部门深度、审批分页大小和最大页数；配置更新接口也支持这些字段。`interval_minutes` 用于任务完成后的下一次执行时间，首次执行仍按 `scheduled_time` 初始化。

### 3. 调度器依赖 API 进程

自动任务在 FastAPI lifespan 中运行。API 进程重启、异常退出或部署多个 worker 时，可能出现：

- 任务中断后留下 `running` 状态。
- 多个 worker 各自启动调度循环。
- 没有独立 worker 时，API 不可用就不会自动同步。

数据库唯一运行任务约束能降低重复执行风险，但不能替代过期任务回收和多进程调度控制。生产环境应至少增加超时 `running` 任务回收；多 worker 部署时应使用单独 worker 或分布式锁。

### 4. 失败恢复依赖当前任务是否写出 cursor

审批分页 cursor 按模板记录，任务失败时保留窗口和 cursor。这个机制能覆盖分页上限和接口异常发生在分页阶段的情况，但实例详情逐条处理失败时，当前逻辑主要依靠整个任务失败后重跑窗口和幂等更新，不能精确跳过已处理到哪一条。

这会增加重试请求量，但不会因为实例 ID 幂等而重复生成有效明细。后续可增加实例级失败列表；当前优先级低于统计语义和调度配置一致性。

### 5. 部门树和模板同步存在额外请求成本

部门树递归过程中会对子部门做重复的子部门查询，模板同步还会针对模板调用流程节点预测接口。部门数量或模板数量较大时，会增加钉钉 API 请求量和限流风险。

应在部门遍历中复用已获取的子部门结果，并考虑对模板节点预测做按模板变化或按时间缓存。两项属于性能优化，不影响当前数据模型正确性。

## 已验证内容

执行命令：

```text
cd apps/api
uv run pytest tests/test_dingtalk_templates.py -q
```

结果：`49 passed`，耗时约 9.71 秒。测试覆盖了自动同步水位、重叠窗口、失败保留 resume 状态、cursor 续跑、稳定审批跳过、待处理审批重刷、模板筛选和审批原始数据落库等行为。

测试中也明确验证了“解析不完整时仍计成功”的现状，因此该问题是当前实现语义，不是偶发环境问题。

## 建议实施顺序

1. 增加过期 `running` 任务回收，生产多 worker 时增加单调度实例约束。
2. 优化部门递归缓存和模板节点预测请求。
3. 需要更高吞吐量时，再增加实例级失败重试记录和独立 worker。

## 结论

主链路已经形成：部门和模板先同步，审批实例按模板分页拉取，详情落库后解析为财务明细，再进入银行流水对账。增量水位、重叠窗口、幂等更新和 cursor 续跑已有实现并有测试支撑。

任务结果统计和自动同步配置接入已修正。当前剩余重点是调度进程可靠性和接口请求成本，属于后续生产稳定性优化。
