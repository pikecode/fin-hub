# 钉钉审批单状态收敛方案

## 背景

当前审批单列表里，用户能看到多个同步/解析中间态：

- `unparsed`
- `pending_classification`
- `pending_match`
- `sync_conflict`
- `matched`

用户希望列表只保留两个状态：

- `已匹配`
- `未匹配`

同时，希望在同步阶段尽量把可自动处理的问题消化掉，减少“同步进来了但还是未解析/待分类”的情况。

## 当前问题

### 1. `unparsed`

常见原因：

- 审批没有完成态
- 关键字段缺失
- 日期字段没有映射成功
- 解析入口没有拿到可用明细

### 2. `pending_classification`

常见原因：

- 明细已解析出来，但分类字段没带上
- 模板映射未配置分类
- 表格列里没有可用的分类来源

### 3. `pending_match`

含义：

- 明细已经解析并分类
- 但还没有与银行流水建立对账关系

### 4. `sync_conflict`

常见原因：

- 审批同步后，源数据发生变化
- 已匹配的明细字段被更新
- 同步删除了部分原有明细

## 目标

1. 列表只展示两态：
   - `已匹配`
   - `未匹配`
2. 同步阶段尽量自动补齐：
   - 日期
   - 金额
   - 分类
   - 可解析明细
3. 保留内部状态用于排障，但不再作为前台主状态暴露

## 拟定方案

### A. 同步时补日期兜底

优先级：

1. 表单中显式的报销/支出日期
2. 审批完成时间
3. 审批提交时间

目的：

- 减少因日期缺失导致的 `unparsed`

### B. 同步时补明细兜底

优先级：

1. 表格明细
2. 分期/分项字段
3. 审批总金额生成单行明细

目的：

- 让没有表格明细的审批，也能落成可对账的费用行

### C. 同步时补分类

优先级：

1. 明细行自己的分类
2. 表单映射里的一级/二级分类
3. 继承审批头部可用分类

目的：

- 减少 `pending_classification`

### D. 同步时处理冲突

策略：

- 已匹配明细不直接覆盖用户已确认的关键字段
- 如果源数据变更，保留冲突标记供排查
- 列表层仍只显示 `未匹配`

### E. 列表状态收敛

前台只保留：

- `matched` -> `已匹配`
- 其他状态 -> `未匹配`

## 需要确认的边界

1. `未匹配` 是否要继续细分到详情页，而不是列表页。
2. `sync_conflict` 是否要在详情页单独提示。
3. 是否允许“没有分类”的审批单进入列表，只要它已形成费用明细。

## 验收标准

1. 审批单列表只显示 `已匹配` 和 `未匹配`。
2. 同步后，能自动落库的审批尽量进入 `matched` 或至少不是 `unparsed`。
3. 对于字段完整但未匹配的审批，仍能进入后续对账流程。
4. 已匹配记录被重新同步时，不破坏已确认对账结果。

## 后续实施顺序

1. 先补同步兜底。
2. 再收敛列表状态文案。
3. 最后补充同步日志和冲突详情。

已完成：

1. 审批日期兜底统一为：
   - 表单业务日期
   - 审批完成时间
   - 审批提交时间
2. 同步解析门槛调整：
   - 不再因为审批头部金额缺失就直接跳过
   - 如果表格明细或分期明细能计算出金额，继续生成费用明细
   - 只有最终总额仍不可用时，才保留为内部 `unparsed`
3. 审批单列表状态展示已收敛为：
   - `已匹配`
   - `未匹配`

未做：

1. 没有新增系统默认分类。
2. 没有覆盖用户在匹配时手动维护的分类。
3. 没有改变已匹配审批单的保护逻辑。
