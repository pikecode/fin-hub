## 一、问题现象

### 观察到的行为

```

├─ 时间范围: 2026-05-26 ~ 2026-09-03

```

## 二、根本原因：钉钉 API 的"去重"机制

### 2.1 钉钉 API 的工作原理

```
第一次查询 (被取消任务):
┌─────────────────────────────────────┐
│ 请求: GET /approval_instances       │
│ 参数: start_at=2026-05-26, end_at=2026-09-03
│ 分页: page=1 (cursor=null)          │
└─────────────────────────────────────┘
         ↓
    钉钉服务端
┌─────────────────────────────────────┐
│ 内部维护的状态:                       │
│ ┌─ instance_id_1: 已返回             │
│ ├─ instance_id_2: 已返回             │
│ ├─ instance_id_3: 已返回             │
│ ├─ ...                              │
│ └─ instance_id_499: 已返回           │
│                                     │
│ cursor_position = page_5_end        │
└─────────────────────────────────────┘
         ↓
    返回 499 条审批 + 游标信息
         ↓
    客户端收到但任务被 canceled ❌
    (数据未保存到本地 DB)
    但钉钉服务端仍记得这 499 个 ID
```

### 2.2 问题发生的时刻

```
第二次查询 (新的全量同步):
┌─────────────────────────────────────┐
│ 请求: GET /approval_instances       │
│ 参数: start_at=2026-06-01, end_at=2026-09-03
│ 分页: page=1 (cursor=null)          │
└─────────────────────────────────────┘
         ↓
    钉钉服务端
┌─────────────────────────────────────┐
│ 检查内部状态:                        │
│ ┌─ instance_id_1: ✅ 已返回过         │
│ ├─ instance_id_2: ✅ 已返回过         │
│ ├─ instance_id_3: ✅ 已返回过         │
│ ├─ ...                              │
│ ├─ instance_id_499: ✅ 已返回过       │
│ │                                   │
│ └─ new_instance_id_500: ❌ 新增      │
│    new_instance_id_501: ❌ 新增      │
│    ...                              │
│    new_instance_id_504: ❌ 新增      │
│                                     │
│ ⚠️ 去重策略:                         │
│ "我只会返回【新增】的审批"            │
│ "已返回过的 ID 不再返回"             │
└─────────────────────────────────────┘
         ↓
    只返回 5 条新增审批 ⚠️
    (那 67 条早期审批被永久跳过了)
         ↓
    客户端保存这 5 条到 DB
```

## 三、为什么其他数据也会有这个问题？

### 3.1 风险场景

```
场景 1: 当前已发生 ❌
─────────────────────
任务 A (5 页): 成功返回 500 条 → canceled
  └─ 钉钉记住: instance_id_1 ~ instance_id_500 已返回

任务 B (全量): 查询相同/更宽的范围
  └─ 钉钉: "这些 ID 我都见过了"
  └─ 结果: 只返回新增的 5 条

场景 2: 未来会发生 ❌
─────────────────────
假如今天同步失败在第 10 页:
  └─ 前 9 页 (900 条) 被钉钉标记为"已返回"
  └─ 第 10~N 页的审批永远无法获取
  └─ 持续累积

场景 3: 每次失败都叠加 ❌
─────────────────────
周一: 同步失败 → 丢失 A 批数据
周二: 新同步运行 → 无法捡起周一的数据
周三: 又发生失败 → 再丢失 B 批数据
... 持续累积无法恢复的数据缺口
```

### 3.2 为什么会这样设计？

```
钉钉的出发点（合理的）:
├─ 防止重复创建支出记录
├─ 减少数据库操作
├─ 确保幂等性
└─ 提高性能

但对我们的冲击:
├─ 一旦同步失败或被取消
├─ 这批数据就永久无法获取
├─ 没有"重新扫描"的选项
└─ 导致数据库中的数据永远不完整
```

## 五、解决方案

### 5.1 短期修复 (应急)

```
方案 A: 从被取消任务的孤立数据恢复 ⚠️ (最多恢复 ~400 条)
────────────────────────────────────
方法:
  1. 查询被取消任务中的审批记录
     SELECT * FROM approval_instance 
     WHERE synced_job_id = '7a8e80f58764434e8d6697c4cd8ffed7'
  
  2. 检查这些记录是否完整 (有钉钉 instance_id、支出等)
  
  3. 将它们的 synced_job_id 更新为成功的任务 ID
     UPDATE approval_instance 
     SET synced_job_id = 'e056ab5ee0bd416bad8a8291f5d35f03'
     WHERE synced_job_id = '7a8e80f58764434e8d6697c4cd8ffed7'
  
  4. 验证这些数据的完整性

风险:
  • 不能保证数据完整性
  • 孤立数据可能已部分损坏
  • 需要人工验证

预期效果:
  • 最多恢复 ~255 条 (其中 3 条是三店的)
  • 系统中还会遗留 ~244 条无法恢复的数据
```

### 5.2 长期方案 (根本修复)

```
方案 B: 与钉钉沟通提供特殊接口 ✅ (最好的方案)
──────────────────────────────
联系钉钉技术支持:
  1. 说明情况: 我们的同步任务在中途被取消或失败
  2. 需要: 提供一个"回溯同步"接口
     ├─ 即使这些 instance_id 已被标记为"已返回"
     ├─ 也能再次获取完整数据
     └─ 用于灾难恢复场景
  
  3. 或者: 提供一个"清除已返回标记"的接口
     └─ 让我们可以重新扫描某个时间范围
  
  4. 或者: 提供一个"全量导出"接口
     └─ 不依赖分页去重机制

预期效果:
  • 永久解决这个问题
  • 系统具备灾难恢复能力
  • 适用于所有失败场景
```

### 5.3 架构层面的改进 (预防)

```
方案 C: 改变同步策略 ✅ (我们可以做)
────────────────────────────────
1️⃣ 实现"同步检查点" (Checkpoint)
   ├─ 同步前记录: start_at, end_at, total_count
   ├─ 同步后验证: 是否获取了预期数量
   ├─ 如果少了，立即重试不同的时间范围
   └─ 不依赖单次查询获取全部

2️⃣ 实现"多维度去重"
   ├─ 不只依赖 instance_id 去重
   ├─ 同时用钉钉订阅/webhook 补充
   ├─ 查询变更日志而不是重新列举
   └─ 减少对 API 分页去重机制的依赖

3️⃣ 实现"失败自动恢复"
   ├─ 同步失败 → 不立即标记为"成功"
   ├─ 下次启动时重新扫描前面的时间段
   ├─ 确保没有遗漏
   └─ 即使前次失败也能恢复

4️⃣ 实现"审计日志"
   ├─ 记录每次同步的实际处理数
   ├─ 与预期数对比
   ├─ 差异时告警
   └─ 及时发现数据缺口
```
