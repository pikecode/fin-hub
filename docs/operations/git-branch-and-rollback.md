# 分支管理与代码回退规范

生效日期：2026-11-09。适用于功能、修复、配置和文档等每批改动。

## 分支约定

| 分支 | 用途 | 保留规则 |
| --- | --- | --- |
| `main` | 已合并的主线代码；实际生产版本以部署记录为准 | 不强推、不重写历史 |
| `work/YYYYMMDD-topic-NN` | 单批开发，NN 用于同日重名区分 | 合并后可保留 |
| `backup/YYYYMMDD-topic-NN-before` | 该批修改前的明确提交 | 永久保留，不移动、不覆盖 |
| `backup/YYYYMMDD-topic-NN-after` | 该批完成验证、提交后的版本 | 永久保留，不移动、不覆盖 |
| `rollback/YYYYMMDD-topic-NN` | 基于最新主线创建的回退操作分支 | 回退提交合并后保留记录 |

备份分支只记录已提交代码，不能保护未提交文件、环境变量、上传附件或数据库。备份分支须随获授权的推送一起推到 origin，只有本地分支不能称为远程备份。禁止通过 `branch -f` 或强推复用备份名称。

## 每批操作

1. 查看 `git status`、当前分支、远程主线及未合并改动。已有用户修改先确认所属批次，不擅自清理。
2. 在修改前提交建立 before 备份，从该基线建立 work 分支，再开始编辑。若之前已直接改 main，明确真实修改前提交，补建备份并注明补建，不能假称事先建立。
3. 记录变更，执行与改动相关的测试，检查暂存区排除密钥、数据库备份和构建缓存，提交完整文件。
4. 用户要求合并/推送时，先拉取远程；有他人更新就先解决冲突并重新验证。正常快进或 merge 合并主线，保留批次提交边界，禁止强推。
5. 最终提交创建 after 备份。使用原子推送一次更新 main 和两个备份分支；远程不支持原子推送时先推备份，验证后再推 main。
6. 用 `git ls-remote` 比较远程分支与本地提交一致；交付时列明提交号和备份名。部署时同时记录该批代码提交、镜像标签及迁移版本。

不把“合并到 main”自动当作“部署成功”。未完成能力、未发布代码必须在 CHANGELOG 说明。

## 如何回退

只查看旧版本时，可从 before 分支创建独立 worktree，避免覆盖当前工作目录：

```sh
git worktree add --detach ../fin-hub-before origin/backup/20261109-finance-miniapp-01-before
```

撤回本批功能时，在干净工作区从最新 origin/main 建 rollback 分支；先为当前主线创建新的 before 备份，再执行：

```sh
git revert a7c4e4e
```

这会创建反向提交并保留后续分支规范文档。若出现冲突或已有后续功能依赖本批，先评估依赖并逐项解决，不能直接用旧版整树覆盖。一般批次应列清该批所有代码提交，按由新到旧顺序 revert；合并提交需明确主线父节点后再处理。测试通过并获推送授权后合并回 main，记录回退提交与新的 after 备份。

生产回滚另按 [增量部署流程](incremental-deployment.md) 执行。本批迁移 0044/0045 新增计提单和余额校正删除字段；旧版余额逻辑不识别已删除校正，发生新业务后不能只换旧镜像。数据库备份恢复会覆盖期间数据，不能作为普通代码回退步骤。
