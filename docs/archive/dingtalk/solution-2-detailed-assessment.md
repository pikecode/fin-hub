## 一、方案② 的核心逻辑

```python
# 改用 modify_time 替代 submit_at
# 这是关键！

旧逻辑 (有问题):
  SELECT * FROM approvals
  WHERE submit_at BETWEEN start_at AND end_at  # ❌ 固定提交时间
  LIMIT offset, 10
  
新逻辑 (方案②):
  SELECT * FROM approvals  
  WHERE modify_time > last_modify_time  # ✅ 追踪修改时间
  AND modify_time <= current_time
  ORDER BY modify_time ASC
  LIMIT offset, 10
  
  记录: last_modify_time = current_time
```

### 为什么 modify_time 不受去重影响？

```
钉钉的去重机制:
├─ 基于: instance_id 的"已返回"标记
├─ 触发条件: 分页查询同一个时间范围
└─ 影响: 返回结果会被去重

modify_time 查询:
├─ 每次查询都是"给我修改过的审批"
├─ 钉钉无法对"修改事件"进行去重
├─ 因为这是基于事件流，不是基于分页列举
└─ ✅ 完全避开去重机制
```

```
  ├─ 状态: canceled
  ├─ 最后 modify_time: 2026-08-28 18:30:15
  └─ DB 更新: NO (task canceled, no commit)

钉钉 API 状态:
  ├─ 旧方案: 记录了"这些 instance_id 已返回过"
  ├─ 去重标记: 对后续分页查询有效
  └─ 影响: 后续查询无法再获取

新方案(modify_time):
  ├─ 钉钉 API 状态: 不变 (无去重标记!)
  ├─ 因为: modify_time 查询不使用分页去重
  └─ 影响: 下次查询仍会获取那 299 条
  
✅ 被取消任务不再是问题！
```
